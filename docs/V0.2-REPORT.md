# StackPilot 0.2.0：真实增量、覆盖范围与验证报告

日期：2026-11-11。对照基线为已交付的 0.1.2 源码包。本版定位仍是个人使用的 Windows 本地 SSH 运维工作台。

## 结论

专业模式已经形成不同于简洁模式的工作流；新增从 Git/文件夹出发、在本机 Docker 构建、经 SSH 交付镜像的完整链路。应用覆盖从成品包扩展到可配置源码构建。八类语言/框架模板完成真实 Linux 构建和 HTTP 运行验证，多服务 Compose 完成实际 SSH 交付。

目前具备覆盖常见 Web 项目的通用路径，但没有统计依据宣称“覆盖绝大多数应用”，也不等于所有应用零配置部署。系统兼容、历史项目接管、数据库集群和特殊依赖仍有明确边界。

公开发布目标为 [clusterstar1229/StackPilot](https://github.com/clusterstar1229/StackPilot)。本报告保留 0.2.0 本地发布时的测试范围；云端 CI 的实际运行记录请查看仓库 Actions，不将提供 CI 配置等同于已通过。

## GitHub 同类项目：取长补短

本轮阅读官方仓库 README/接口文档，未使用社区文章替代实现依据；未复制这些面板的业务源码。项目会变化，下表是本次查阅范围的归纳，不能代替完整产品评测。

| 项目及依据 | 已有能力 / 对 StackPilot 的启发 | StackPilot 本版的选择 |
|---|---|---|
| [Coolify](https://github.com/coollabsio/coolify) | Git 提供商、构建/容器、数据库、部署历史、健康检查、TLS；应用发布应成为连续流程 | 引入源码检测、构建任务、来源记录和发布历史联动；控制面仍在本机 |
| [Dokploy](https://github.com/Dokploy/dokploy) | 多语言、多服务、Compose、模板、监控；不能只做静态网站上传 | 12 个可调整构建方案，Compose 连同镜像和相对文件交付 |
| [1Panel](https://github.com/1Panel-dev/1Panel) | 网站、数据库、主机和备份按资源组织，适合新手 | 简洁模式围绕任务，专业模式围绕资源、配置与版本；不复制 GPL 业务代码 |
| [Electerm](https://github.com/electerm/electerm) | 桌面 SSH/终端/SFTP/远端编辑，专业用户需要真正交互 | 新增真实 PTY、多会话与配置文件编辑，保留可视化发布路径 |
| [Kamal](https://github.com/basecamp/kamal) | 已有客户端通过 SSH/Docker 的无 Agent 部署 | 不把“SSH、无 Agent、本机部署”单独包装成原创；将能力组织成中文桌面向导 |
| [CapRover](https://github.com/caprover/caprover) | 容器应用、Nginx、证书与简化部署相结合 | 保留网站配置集中入口，支持成品包、原生服务和本机源码构建 |

因此，“Git 部署”“完整终端”“Docker/Compose”“自动 HTTPS”“SSH 无 Agent”均不是本项目首创。可说明的产品差异是：**本地 Windows 桌面 + 成品包/源码两入口 + 本机编译后 SSH 交付 + 新手向导/专业工作台 + 常见数据库运维**的具体组合与使用路径。差异是否有市场价值需要真实用户反馈验证。

## 相对 0.1.2 的可核查增量

| 变化 | 0.1.2 | 0.2.0 | 代码入口 / 证据 |
|---|---|---|---|
| 专业模式 | 主要展开高级配置，主体布局接近 | 更窄导航、资源表、YAML 检查器、运行日志、发布记录、最近任务 | `src/expert.tsx`、`src/expert.css`；桌面截图与模式检查 |
| SSH 终端 | 预定义只读诊断 | xterm + SSH2 PTY；多会话、输入、尺寸、切页保留 | `electron/terminal.ts`；正式真实 SSH2 测试及 Linux/原服务器 PTY |
| 源码入口 | 成品包为主 | HTTP(S) Git/本机目录、分支、临时 Token、Commit | `electron/source-build.ts`；认证 Git HTTP 服务克隆测试 |
| 编译位置 | 无统一本机源码构建链路 | 本机 Docker 编译，保存/压缩镜像，经 SSH 上传并 docker load | `source-build.ts`、`deploy.ts`；跨 SSH 实际 HTTP 请求 |
| 语言识别 | 手选类型/入口 | 区分源码、静态输出与 SSR，识别 JAR/WAR/Compose/.NET 等 | `shared/build-profiles.ts`、`inspect-package.ts`；识别回归 |
| 模板 | 运行包部署 | 12 个可修改的源码构建方案 | `shared/build-profiles.ts`；8 个模板运行实测 |
| 配置复用 | 更新需再次选择本机包 | YAML 导入/导出、保留加密环境占位符、远端产物复用 | `shared/recipe.ts`；配置测试、静态/Compose 实际复用发布 |
| Compose | 单 YAML 与远端镜像为主 | 文件夹、多服务镜像归档、相对 bind/config/secret 文件携带 | `source-build.ts`、`deploy.ts`；两个服务、挂载内容实测 |
| 专业文件管理 | 限定本系统应用目录 | 专业模式可编辑 SSH 有权限的配置路径，保存前备份 | `electron/operations.ts`、文件管理界面 |
| 社区可验证性 | 临时测试已按旧要求清理 | 正式测试、可选 Docker 集成、贡献说明、双平台 CI 配置 | `tests`、`.github/workflows/ci.yml`、`CONTRIBUTING.md` |

导出的部署 YAML 移除服务器 ID、本机文件 ID 和环境变量值；同一应用编辑时保留已经保存的加密占位符。构建来源记录保存 Commit、配置和镜像/归档校验值，避免只能看到“部署成功”却无法追溯产物。

Compose 按用户信任的可执行配置运行，不再对真实项目一律禁止挂载/网络选项。保留凭据加密、主机指纹、操作前预览、文件备份及已有资源归属检查；专业终端不拦截操作者的 Shell 命令。

## 应用覆盖矩阵

“本轮实测”表示专门的小型代表项目在本次版本执行成功，不代表同框架任意业务项目均成功。“可配置”表示有实现路径但仍需要验证项目依赖、命令和版本。

| 应用 | 推荐路径 | 本轮状态 / 仍需配置 |
|---|---|---|
| 普通 HTML、React/Vue dist | 上传目录/压缩包 → Nginx | 静态、嵌套 dist、子路径 SPA 已实测；API/域名按项目设置 |
| React/Vite 源码 | static 方案 | 实际 npm 构建与 Nginx HTTP 已通过 |
| Vue/Vite、Angular | static 方案 | 共用构建路径；本轮没有独立 Vue/Angular 业务实测，Angular 输出目录需按项目调整 |
| Node/Express/Nest | node 方案或运行包 | Node 实测通过；Nest 需正确 build/start 脚本，框架业务依赖需联调 |
| Next.js SSR | next 方案 / 项目 Dockerfile | 实际 Next 16 服务端运行通过；不能当静态 dist |
| Nuxt/Nitro | nuxt 方案 | 有 `.output` 识别和运行模板，未独立实测 |
| Spring Boot/Maven | maven 方案 / 上传 JAR | Spring Boot 3.5.7、Java 21、Maven 实际构建启动通过 |
| Spring Boot/Gradle | gradle 方案 | 有 Wrapper/bootJar 模板，未独立实测 |
| 普通 WAR | Docker/Tomcat 10 或自备兼容镜像 | 路径保留，未做本轮普通 WAR 实测；javax/Jakarta 需匹配 |
| FastAPI | python 方案 | 实际依赖安装、ASGI 启动和 HTTP 已通过 |
| Flask/Django | python 方案、自定义模块 | 模块建议已实现；Django manage.py 识别回归通过，未做完整业务实测 |
| Go | go 方案或 Linux 二进制 | 实际 Linux 编译与 HTTP 通过；CGO/额外库需 Dockerfile |
| ASP.NET Core | dotnet 方案或发布包 | .NET 8 构建启动通过，填写实际 DLL 名称 |
| PHP | php 方案 | PHP 8.3/Apache 实测通过 |
| Laravel | php 方案/public，或 Dockerfile | 有 public 根目录和 rewrite 配置；扩展、APP_KEY、存储、迁移需项目配置，未做完整 Laravel 实测 |
| 自带 Dockerfile | Dockerfile 方案 | 本轮构建、归档、SSH 导入、运行、蓝绿/回滚完整实测 |
| 多服务 Compose | Compose 本机构建与归档 | 两镜像、相对配置挂载、SSH 交付、仅改配置发布通过 |
| SvelteKit/Astro/Remix、Ruby/Rust 等 | 自定义 Dockerfile/Compose | 通用容器路径；没有专用识别与零配置承诺 |
| GPU/CUDA、ARM、多架构 | 项目 Dockerfile + 相应构建/运行环境 | 本轮未验证，不自动安装驱动或转换架构 |
| 大型 monorepo、pnpm/yarn/Bun workspace | 修改构建命令/子目录或 Dockerfile | 默认 Node 模板使用 npm，未提供全自动工作区推断 |

所有源码镜像都要求目标具备 Docker。选择原生成品包路径时仍可由 systemd 运行，不强制把原生服务改成容器。软件运行时的实际内存需求仍由应用决定，本机编译只减少目标服务器的编译负担。

## 数据库与主机运维覆盖

数据库模块本版沿用 0.1.2 的实现，没有把旧能力作为本版新增。此前 71 项验证详见 `V0.1.2-VALIDATION.md`，与本次测试分开记录。

| 范围 | 已有实现 | 不能据此承诺的内容 |
|---|---|---|
| MySQL/MariaDB/PostgreSQL | SSH 隧道/Unix Socket、只读 SQL、唯一行修改、建库/账号/授权、备份、新目标恢复、容器安装 | 任意 SQL 编辑、跨所有主版本升级、任意现有架构自动迁移 |
| Redis | 查询/状态/慢日志、ACL、新实例、RDB 备份、同主版本升级、复制模板 | GUI 通用二进制恢复、任意 Redis Cluster 重构 |
| MongoDB | 查询/集合/活动、只读账号、容器初始化、归档备份、复制模板 | 任意 BSON 编辑、跨集合一致时间点备份、GUI 通用 archive 恢复 |
| SQLite | 文件连接、查询、唯一行编辑、备份、新文件恢复 | 服务器没有 sqlite3 CLI 时仍需安装工具 |
| 复制/集群 | 同主机模板，部分引擎此前实测 | 跨主机 HA、自动故障转移、所有引擎/版本均已验证 |
| 现有服务 | 自动发现当前账号可见的 systemd/Docker、日志与启停 | 自动理解所有历史部署，恢复从未记录的发布历史或秘密 |
| 监控/诊断 | 系统指标、HTTP 检查、日志、端口/进程/磁盘等 | 全部运维问题自动诊断修复、桌面关闭后的持续控制面告警 |
| DNS/HTTPS | 三类 DNS API、HTTP-01/续期、上传证书 | 本轮未改真实 DNS/申请证书；无域名授权不能代替解析操作 |

SQL 查询界面继续只读，受控编辑走确认入口；专业 SSH 终端允许操作者自己使用数据库客户端执行管理命令。它不是完整数据库 IDE，也不是所有数据库产品的管理器。

## 本轮验证证据

### 正式回归：17 项通过

覆盖 SSR/静态/源码区分、Compose/JAR/WAR/.NET/嵌套包识别、Django 模块建议、YAML 跨环境复用与敏感值移除、同应用环境占位符、仅改配置发布、蓝绿端口冲突、空/映射 SSH 端口、运行镜像模板；另以真实 Git HTTP 认证后端验证分支 Commit 和 Token 不落盘，以真实 SSH2 服务验证 Unicode 分块、PTY 输入/resize/会话输出保留。

命令：`npm test`。本地 Windows 通过；Ubuntu CI 尚未在 GitHub 实际执行。

### 独立 Linux SSH/Docker：13 项通过

1. 独立 SSH 与 Docker 就绪。
2. 真实交互终端 Unicode/PTY。
3. 本机源码检测、Docker 构建和镜像归档。
4. SSH 上传/导入后 HTTP 返回预期内容。
5. 蓝绿切换到第二版本。
6. 历史回滚到第一版本。
7. 故意以退出码 17 启动失败，健康检查失败后恢复旧服务。
8. Compose 两服务镜像及相对配置归档。
9. Compose 离线导入和多服务运行。
10. 相对文件挂载内容一致。
11. Compose 复用产物修改配置再次发布。
12. 嵌套 dist 与 SPA 子路径真实访问。
13. 复用静态产物修改路由后真实访问。

外层测试容器使用独立私有 cgroup namespace 和内层 Docker 数据卷；测试只连接自己创建的 SSH，完成后清理自身实例。最初 Docker-in-Docker 的 cgroup v2 启动失败已通过在测试容器自己的命名空间内初始化控制组修复，没有修改宿主机全局控制组。

### 桌面与发布检查

## 复现与发布

`tests/README.md` 提供正式与可选集成命令，fixture 不包含真实服务器口令。CI 仅使用 GitHub 临时 Windows/Ubuntu 测试机执行回归与源码编译，不生成或上传安装包，不构建或推送 Docker/系统镜像。生产依赖许可证元数据由 `npm run notices` 更新；使用 xterm、ssh2、isomorphic-git 等公开库，不复制其他运维面板。

发行渠道按既定决策分开：GitHub 托管 StackPilot 源码；服务器仅部署独立静态安装包下载服务、校验和与版本元数据，不上传桌面源码、不安装构建环境。公网新端口的云端放行规则须单独确认。

## 后续优先级建议

1. 补实际用户项目兼容性：pnpm/yarn、更多 monorepo、Nuxt/Gradle/普通 WAR、LFS/子模块与 ARM。
2. 增加明确版本的应用模板目录，先覆盖常见开源应用，再逐项提供可复现健康检查，而非扩大“全部支持”的宣传。
3. 现有服务导入助手：读出启动方式/目录/端口后由用户核对，保留原部署，不盲目重写配置。
4. 数据库补图形恢复与更完整的数据编辑；跨主机 HA 单独设计和压测。
5. 发布 GitHub 仓库后收集 issue、运行云端 CI，并逐步补代码签名和更新分发。
